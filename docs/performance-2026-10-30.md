## 生产路径盘点及修改

1. **冷读取和保存的 CRC**：旧 `Durable.load → unpack` 为 `crc32(utf8(json))`，先创建数值数组、再复制成 Uint8Array、再扫描计算 CRC；`revision` 和保存也走同一路径。现在在严格 UTF-8 编码过程中直接累计 CRC，不创建整串字节数组，原 UTF-8/CRC 位级结果保持一致。没有跳过冷启动完整性校验。
2. **保存冻结**：旧 Durable.save 先 stringify→parse 冻结，排队时再 stringify。现在在调用时冻结成 JSON 文本，排队只计算同一文本的校验与封套。调用后修改输入不能改变待保存结果；双槽写入、回读原文一致性、指针提交和失败保护保留。
3. **完整引用校验**：为已验证集合建立本次调用内的 Set/Map；引用、时段、轮换、日期、临时补丁等检查全部保留。没有用缓存绕过对新档案的检查。保留原验证器作 200 组接受/拒绝原因对照。
4. **菜单和列表绑定**：原每行 `Object.keys(actions).length` 反复枚举已建动作，500 科目菜单每次刷新枚举 502 次。现在单调编号；内容未变化的 rows 保留引用，而动作回调仍更新到最新档案，避免状态提示变化时重建列表。每秒倒计时原来已不替换 rows，本轮继续保持，未把这个已有优化重复计为新增。
5. **首屏依赖**：Main 原来虽延迟 native require，却仍顶层导入 BLE→Link→transport→LZ4/finalization 等 JS。现在完整可选 JS 模块也按使用 require；隐藏/退出不会为了 stop 而首次加载 BLE。存储 native 接口在实际打开时加载并单独计时；第一份首页绑定之前不加载同步、卡查询、反向角色或共享模块。在 Node 中执行真实 Main UX 的 script、mock 存储与系统接口的生命周期/按钮测试验证这一点；不是 BlueOS 原生渲染测试。
6. **首页后共享**：首次版本哈希采用有界 canonical 文本块和合作式让出，避免一次创建/编码整份 canonical 文本。达到工作量阈值或时间预算后让出事件循环；8 ms 是检查预算，不是对 GT2 最大阻塞的保证。版本仍与原 canonical CRC 完全一致。后续相同不可变档案引用缓存版本和当日解析；新档案、偏移、临时边界、回拨、跨日仍失效。摘要使用异步版本计算完成后的真实时间，避免计算跨过边界后发布旧时点状态。串行 exchange 写入并成功后发事件，防旧异步发布覆盖新结果。
7. **同步收尾**：只对已经归接收器所有的内存缓冲省去额外复制，解码用只读 subarray；默认外部输入仍复制保护。原生 ArrayBuffer 进入链路时仍先复制。分段粒度和严格解码不放宽；取消在下一分段立即停止工作，仍保留 END、预览落盘与 SAVED 保护。
8. **诊断细分**：启动诊断区分存储接口加载、指针/正文 IO、封套解析、正文 CRC、正文解析、引用检查、首页绑定，记录正文 UTF-8 字节数、冷读取/进程缓存、累计与阶段值。共享另列 JS 模块加载、版本缓存命中、版本计算（含让出）、最长连续版本计算段、课程解析、native 提交/native 完成和事件耗时。页面明确计时起点不是图标点击至首帧；没有伪造绘制指标。

## 可复现合成对照

命令：

```sh
node blueos/scripts/performance-bench.mjs
node --jitless blueos/scripts/performance-bench.mjs
```

脚本从固定 Git 基线读取原生产模块，在独立临时目录加载；比较同一组输入，3 次预热、7 批交替顺序，报告每次操作的中位数。普通 Node 和 --jitless 都是 V8，不是 BlueOS VM。所有课表、教师和正文均为合成数据，不使用用户截图档案。

本次 Node 24.19.0；档案 21,791 B，存档正文 87,231 B。冷加载测试使用内存 IO，未计设备存储、模块解析、实际绘制。共享计算测试让出回调为已完成 Promise，不能用来预测真机总墙钟延迟。

| 对照项 | 普通 Node，基线 → 本轮 | Node --jitless，基线 → 本轮 |
| --- | --- | --- |
| UTF-8 CRC（16,000 UTF-16 单元 / 28,000 B） | 0.331 → 0.058 ms | 1.820 → 1.048 ms |
| 完整存档加载校验（内存 IO，含两次 JSON 解析） | 1.350 → 0.487 ms | 6.540 → 3.923 ms |
| 双槽保存（冻结、编码、CRC、回读） | 0.838 → 0.249 ms | 3.733 → 2.104 ms |
| 引用校验（100 科目 / 8 课表 / 24 时段） | 0.038 → 0.030 ms | 0.097 → 0.055 ms |
| 500 科目菜单刷新 | 0.770 → 0.065 ms | 0.804 → 0.195 ms |
| 首次共享摘要计算（让出回调为已完成 Promise） | 0.503 → 0.399 ms | 1.975 → 1.923 ms |
| 重复共享摘要（不可变档案缓存） | 0.480 → 0.003 ms | 1.911 → 0.006 ms |

原始数据：[普通 Node](performance/node-2026-10-30.json)、[--jitless](performance/jitless-2026-10-30.json)。首次共享总计算量仅小幅改善，主要收益是让出和后续缓存；不能将其解释成 653 ms 在真机上按某倍数缩短。实际 macrotask 调度和 native exchange 等待仍需新真机读数。

确定性的操作量对照：500 科目菜单枚举 actions 次数 **502 → 0**；Durable.save 的 JSON.parse 次数 **1 → 0**、JSON.stringify 次数 **3 → 2**。CRC 中间整串 UTF-8 数组被移除，但必要的存储 JSON 文本仍保留。
